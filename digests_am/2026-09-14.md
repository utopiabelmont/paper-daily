### 四、复核方法与其局限

- **方法**：`arxiv.org/list/<cat>/recent?show=2000` 取回 6 个分类的完整列表 → 按 `<h3>` 公告日分段，取 9/9、9/10、9/11 三天 → 对 `digests/` 与 `digests_am/` 共 366 个历史 ID 去重 → 逐篇抓 `arxiv.org/abs/<id>` 取摘要原文 → 用 `fetch_arxiv.py` 自己的 `server_terms` 短语表与 `relevance_score()` 复算。
- **覆盖是穷尽的**：三个公告日在 6 个分类上均为完整列表（无「showing 50 of 89」式截断），949 篇 abs 页 **0 失败**。这一点与主方向今日简报不同——那边 cs.CV / eess.SP 存在截断、只能确认核心两类无漏检；**本方向这次没有覆盖缺口。**
- **局限**：复核只覆盖 9/9–9/11 三个公告日。更早的公告日若有本方向论文而历史简报漏报，本次不会发现——但那属于往期问题，不影响今日结论。

### 五、修复建议（优先级从高到低）

1. **前沿探测失败时，绝不能退回「当前时刻」。**（`fetch_arxiv.py` 第 209–210、219–220 行）当前逻辑打一行 warn 后 `return None`，再按 `now - 72h` 算窗口。这个退路方向是反的——数据源越滞后，窗口越偏离真实数据。建议改为：优先退回「上一期记录的前沿」，取不到则**非零退出**，让 routine 显式失败。
2. **全部页面抓取失败时非零退出。**（`fetch_arxiv.py` 第 252–258 行）当前每页失败只打一行 warn 就 `continue`，三页全败仍走完流程、写出「0 篇」、退出码 0，产出的候选清单与真正的空窗日**在格式上完全一致**。建议统计成功页数，为 0 则非零退出，并在 `candidates_am.md` 顶部写明「抓取失败，本文件不代表检索结果」。
3. **把「跳过历史重复数」当健康指标。** 该数正常为个位数到二十几，一旦归零基本可断定是抓取失败而非空窗，比看候选篇数灵敏得多。
4. **重试策略对限流不友好。** 当前退避是 `5/10/15/20/25/30` 秒线性递增，6 次重试在约 105 秒内打满。对按时间窗计数的限流来说，这种密集重试**会主动烧光自己的配额**——今天限流在会话内逐步收紧很可能与此有关。建议改指数退避、遇 429 至少等 60 秒、总重试次数降到 3 次。
5. **加一条替代通路兜底。** 今天已验证 `arxiv.org/list/<cat>/recent` + `arxiv.org/abs/<id>` 在 API 被限流时完全可用，且能做到穷尽覆盖。建议把它固化成 `fetch_arxiv.py` 的 fallback，在 API 全败时自动接管，而不是每次靠人工临时复核。
